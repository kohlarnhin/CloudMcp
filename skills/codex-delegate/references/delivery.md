# 验收、Git 提交和发版

## 验收依据

复跑当前环境支持的测试、构建或检查。因工具链或沙箱限制无法运行的必要检查，按 [CloudMCP 调用说明](cloudmcp.md) 的验证限制另行安排，由调用者核对结果，并记录执行者、环境和结果。查看与原始 `HEAD` 相比的 diff 和相关未跟踪文件，检查错误路径、回归以及是否超出范围。检查 Codex 是否跳过或削弱验证，是否留下临时代码或凭据。对用户可见的改动，用项目的真实运行环境核实关键交互。

维护一份审查决定，可以写入 `execution_review.note`。为每个确认的问题写清依据和处理结果。保留重要的拒绝或部分采纳理由。存在明确的失败项时记录 `needs_work` 并推进修复。满足验收条件后写 `completed`，附实际检查和证据。

## 调用者提交

在用户或长期工作指令已授权提交的开发交付任务中，验收通过后直接由调用者执行提交，并等待命令结束。提交需要满足以下条件。

- 任务改动已核实，确认的问题都已解决或有明确的处理决定，实际验收结论为通过。
- 当前分支和 `HEAD` 对得上开工基线或上一个已确认的任务提交。已有改动、其他人后续提交或切换分支时，先确认改动归属和提交目标。
- 选定明确属于任务的文件。使用 `git --literal-pathspecs add -A -- <本次文件>`，再用 `git --literal-pathspecs commit --only -m <说明> -- <同一组文件>`，每个路径和消息按 Shell 规则引用。目录重命名或文件删除需要将涉及的原路径和新路径一起核对。包含已有用户改动的文件要先隔离本次内容，整体提交该文件会包含其工作树内容。
- Git hooks 正常运行。修复可恢复的失败后复验并重试。作者身份缺失时使用已有仓库级配置或用户给出的身份。遇到响应丢失时先看执行记录与 Git 历史，复用原 `request_id` 查询该次命令。

提交后用 Git 验证 SHA、包含的文件和仍在暂存区的无关改动。若检查确认没有任务改动，直接报告实际状态。若因具体阻塞未能提交，说明失败的命令和仍待提交的改动。

## 调用者发版

先读项目关于版本、测试、构建、签名、打标签和发布的要求。发布目标和外部操作以用户的现有授权为准。已批准发版时，调用者将发布步骤作为本任务的交付动作，通过 `command_exec` 或项目提供的发布工具亲自执行。可以让 Codex 准备候选改动、测试或构建产物，提交、打标签、推送、创建 Release、上传发布资产和部署由调用者执行。

发版前核对对应提交、版本以及检查结果，按项目要求完成构建、签名或其他验证。发布后检查目标版本和标签指向的 SHA，核实已发布的资产或部署状态，向用户报告实际结果及证据。遇到发布凭据或目标不可用时，保留已验证的提交和产物，指出具体失败条件。
